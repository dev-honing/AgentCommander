# Phase 6 초안 — 목업을 LangGraph로 교체하기

목업 상태 루프를 실제 오케스트레이션으로 바꾸는 단계의 밑그림이다. **확정안이 아니라 논의를 위한 초안**이며, 특히 1장은 사용자 결정이 필요하다.

> 명세는 오케스트레이션 프레임워크를 LangGraph로, 구조를 "서브에이전트 1개 = 그래프 1개(독립 실행)"로 확정했다. 다만 **"서브에이전트가 실제로 무슨 일을 하는가"는 미정으로 남겨 두었다.** 그게 정해져야 그래프를 짤 수 있다.

---

## 1. 먼저 정할 것 — 에이전트는 무슨 일을 하나

이 도구의 가치는 "여러 에이전트가 동시에 뭘 하는지 한눈에 본다"는 데 있다. 따라서 첫 실작업은 다음 조건을 만족해야 한다.

- **동시에 여러 개**가 돌아간다 (5~20개 규모를 명세가 전제)
- **상태가 다양하게 갈린다** — 특히 `waiting`, `retrying`, `error`가 실제로 나와야 한다
- **결과를 사람이 알아볼 수 있다** — 데모에서 "이게 뭘 한 거냐"에 답할 수 있어야 한다
- **외부 의존이 적다** — LLM API 하나면 충분한 것

### 후보

**A. 리서치 파이프라인** — 질문 하나를 받아 여러 에이전트가 나눠 조사하고 종합한다.

```
질문 "AgentCommander 같은 도구의 경쟁 제품은?"
  ├─ researcher-1  웹 검색 → 후보 수집
  ├─ researcher-2  다른 각도로 검색
  ├─ reviewer      수집 결과 교차 검증
  └─ writer        최종 정리
```

시드된 역할(`researcher`/`coder`/`reviewer`)과 자연스럽게 맞고, 검색 호출이 실패·재시도를 자주 만들어 `retrying`/`error` 연출이 살아난다. 결과물이 문서라 데모에서 보여주기도 쉽다.

**B. 코드 리뷰** — diff를 받아 관점별로 나눠 검토한다.

```
diff
  ├─ 버그 관점
  ├─ 성능 관점
  ├─ 보안 관점
  └─ 종합
```

개발자에게 가치가 명확하고 입력을 구하기 쉽다(이 레포의 커밋을 그대로 쓰면 된다). 다만 역할 이름이 관점별로 바뀌어야 해서 캐릭터 매핑을 다시 잡아야 한다.

**C. 범용 작업 큐** — 프롬프트를 넣으면 에이전트 하나가 처리하는 형태.

가장 단순하지만 "왜 여러 개를 동시에 보나"라는 이 도구의 전제가 약해진다.

### 추천

**A(리서치 파이프라인)** 를 권한다. 역할 시드를 바꾸지 않아도 되고, 명세의 예시 메시지("웹 검색 중...", "리서치 결과 3건 찾음")가 이미 이 방향을 가정하고 있다. 무엇보다 **의도적으로 실패를 만들지 않아도 자연스럽게 재시도가 발생**해서, 이 도구가 풀려는 문제("조용히 재시도만 반복하는 에이전트를 놓치지 않는다")가 데모에서 저절로 드러난다.

**결정 후에야 아래 2장부터 확정할 수 있다.**

## 2. 교체 지점

명세 2.2절이 정한 경계를 지킨다. **바뀌는 것은 `orchestrator.py` 하나뿐이고, WebSocket 스키마와 프론트엔드는 손대지 않는다.**

```
                        지금                        Phase 6
                 ┌──────────────┐            ┌──────────────┐
                 │ mock_state_  │            │  LangGraph   │
                 │    loop()    │            │   그래프 N개  │
                 └──────┬───────┘            └──────┬───────┘
                        │  apply_transition()       │  노드 진입/이탈
                        ▼                           ▼
                 ┌────────────────────────────────────────┐
                 │  db.upsert_agent()  +  hub.broadcast()  │  ← 이 계약은 그대로
                 └────────────────────────────────────────┘
```

즉 LangGraph 노드가 할 일은 **작업 수행 + 상태 보고** 두 가지뿐이고, 보고 방식은 지금 목업이 쓰는 것과 동일하다.

```python
# 노드 안에서
agent.state = AgentState.RUNNING
agent.message = "웹 검색 중..."
await report(agent)          # upsert_agent + broadcast 를 감싼 함수
```

`report()` 하나만 만들어 두면 목업과 실제 로직이 같은 통로를 쓴다. 나란히 돌려 보며 교체할 수 있다.

## 3. 상태 매핑

LangGraph 실행 흐름을 `AgentState`에 어떻게 대응시킬지가 핵심이다.

| AgentState | 언제 |
|---|---|
| `idle` | 그래프 시작 전, 또는 완료 후 대기 |
| `running` | 노드 실행 중 (LLM 호출, 도구 실행) |
| `waiting` | 다른 에이전트의 결과나 외부 응답을 기다리는 중 |
| `retrying` | LangGraph `RetryPolicy`가 재시도를 걸었을 때 |
| `error` | 재시도를 소진하고 최종 실패 |
| `done` | 그래프가 끝까지 도달 |

**`waiting`이 실제로 나오게 하려면** 에이전트 사이에 의존이 있어야 한다. 리서치 파이프라인이라면 종합 담당이 조사 담당들의 결과를 기다리는 구간이 그렇다. 의존이 없으면 이 상태가 영영 안 나오고, 존 하나가 빈 채로 남는다.

`progress`는 그래프의 전체 노드 수 대비 통과한 노드 수로 잡으면 자연스럽다.

## 4. 재시도

명세 11.2절이 정한 대로 LangGraph의 `RetryPolicy`를 쓴다. 설정값은 이미 `config.py`에 있다.

```python
retry_policy = RetryPolicy(
    max_attempts=settings.max_retry_count,             # 3
    initial_interval=settings.retry_initial_interval,  # 1.0
    backoff_factor=settings.retry_backoff_factor,      # 2.0  → 1s, 2s, 4s
)
graph.add_node("call_llm", call_llm_node, retry=retry_policy)
```

**주의**: `RetryPolicy`는 재시도를 조용히 처리한다. 화면에 `retrying`이 뜨게 하려면 노드 안에서 시도 횟수를 직접 감지해 보고해야 한다. LangGraph가 재시도 콜백을 제공하지 않으면, 노드 함수 안에서 try/except로 감싸고 직접 세는 편이 확실하다.

지금 목업이 만든 계약(`retry_count`를 포함한 `agent_update`, 소진 시 `error`)을 그대로 지키면 프론트는 수정이 필요 없다.

## 5. 데이터 모델 변경

에이전트가 실제 일을 하려면 "무엇을" 할지가 필요하다. 현재 `agents` 테이블에는 그 자리가 없다.

| 추가 | 용도 |
|---|---|
| `task` 또는 `prompt` | 이 에이전트가 받은 작업 |
| `result` | 산출물 (길면 별도 테이블) |
| `parent_id` | 어느 작업에서 갈라져 나왔는지 |

`parent_id`가 있으면 나중에 3D 씬에서 **에이전트 사이의 관계를 선으로 잇는** 연출도 가능하다. 지금 당장은 아니어도 컬럼만 미리 잡아두는 편이 싸다.

작업 단위를 묶는 `runs` 테이블(질문 하나 = run 하나)도 필요할 가능성이 크다. 1장 결정 후에 확정한다.

## 6. LLM 어댑터 마무리

`llm/adapter.py`는 인터페이스만 있고 구현이 비어 있다. 명세 11.1절이 목표한 "노드는 provider를 모른다"를 지키려면 통일 메서드를 가진 래퍼가 필요하다 — 이유는 `docs/SPEC-NOTES.md` 8번 항목 참고.

```python
class LLMClient(Protocol):
    async def complete(self, messages, *, model, max_tokens=1024) -> str: ...
```

Anthropic / OpenAI 두 구현을 채우고, 모델 ID는 하드코딩하지 말고 설정이나 역할 정의에서 주입받는다.

**비용 주의**: 20개 에이전트가 동시에 LLM을 호출하면 순식간에 쌓인다. 개발 중에는 `MOCK_AGENT_COUNT`처럼 동시 실행 상한을 두거나, LLM 호출을 흉내만 내는 모드를 남겨 두는 편이 안전하다.

## 7. 진행 순서

한 번에 갈아끼우지 않는다. 각 단계마다 화면이 계속 돌아야 한다.

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 6a | `report()` 도입, 목업을 그 위로 이전 | 화면 동작 그대로, 코드만 정리됨 |
| 6b | LLM 어댑터 구현 + 단일 노드 그래프 | 에이전트 하나가 실제 LLM을 부르고 상태를 보고 |
| 6c | 다중 에이전트 + 의존 관계 | `waiting`이 실제로 발생 |
| 6d | 재시도 연동 | 실패를 유도했을 때 `retrying` → `error` 흐름 확인 |
| 6e | 목업 루프 제거 | `BACKGROUND_TASKS_ENABLED` 로 전환 |

**6a는 지금 바로 할 수 있다.** 1장 결정을 기다리지 않아도 되고, 나중 교체를 훨씬 쉽게 만든다.
